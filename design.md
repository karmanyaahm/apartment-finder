# Apartment finder: design

Living document. Source of truth for architecture. Any change to behaviour, schema, config shape or a decision updates this file and appends to the [decision log](#decision-log) in the same commit (see `AGENTS.md`).

## Context

A personal tool that runs locally (SQLite plus files on disk, web app on `127.0.0.1`, later exposed through a Cloudflare tunnel). The search has two goals that stay separate but share one global candidate list. The main output is a map dashboard that takes manual comments, ratings and verification checks.

## Goals (`config/goals.toml`)

The goals below are the committed example (`config.example/goals.toml`); the real ones live in the gitignored `config/`.

| | Goal 1: `temp` | Goal 2: `lease` |
|---|---|---|
| What | Airbnb, Furnished Finder, Blueground or similar furnished stay for one person | Apartment or house for a group |
| Sizes | private room is fine; bathroom must be private | 3bd with 2 or more baths (3/2, 3/2.5, 3/3) |
| Dates | Dec 1, 2026 to Jan 1, 2027 | from about Jan 1, 2027; availability ignored for now |
| Hard filters | at most 8 min bike, or at most 25 min walk or transit, to downtown Palo Alto; private bathroom; furnished; at most $4,000 a month | under $2,500 per bedroom; long-term lease |
| Nice to have | none | at or under $2,000 per bedroom; gym; walk to Caltrain 20 min or less; Google bus stop nearby (list supplied later); living room size or total sqft |

## Principle: gather wide, filter late

- **Ingest takes everything in the area**, whatever its beds, baths or price. Goals are filters over stored data, so changing a threshold or adding a goal needs no new scrape.
- **Everything is timestamped and kept.** Each fact carries when it was observed and which source and run produced it. Nothing is overwritten or deleted.
- **Unknown never rejects.** Any filter whose input is missing passes the place with `needs_check` and names the missing field.
- **Filters report, they do not drop.** A failing place stays in the database and on the map (dimmed) with its fail reasons.
- **Paid routing is the one lazy step.** Straight-line distance is computed for everything for free. Google routing runs first for places passing a loose straight-line prefilter, and on demand for any other place from the dashboard.

Search area (`config/area.toml`): every city along Caltrain from Redwood City to Sunnyvale: Redwood City, North Fair Oaks, Atherton, Menlo Park, Palo Alto (including Stanford), Los Altos, Mountain View, Sunnyvale.

## Storage: logs are the truth, entities are derived

One SQLite file `data/apartments.db`, plus `data/raw/` (untouched scraper output, one JSON file per run and source) and `data/media/` (mirrored photos and floor plans named by content hash, because listing image URLs expire). `data/` is gitignored. Seed/demo data lives in a separate file, `data/seed.db`, so it never mixes with real observations.

### Append-only logs

Triggers reject UPDATE and DELETE on every log table. The only exception: a `runs` row may be updated once to close it out (`finished_at`, `counts`, `est_cost`, `status`, `error`) while its `finished_at` is still NULL; its identifying columns can never change.

- `runs`: id, started_at, finished_at, component, source, `params` JSON, `counts` JSON, est_cost, status (`running`, `ok`, `error`, `aborted`), error. `params.scope` is `full` (the whole area for that source; the default) or `targeted` (e.g. direct enrichment of one place). A listing is `active` when its latest observation is from, or newer than, its source's latest successful full run; targeted runs never mark anything inactive.
- `observations`: id, run_id, observed_at, source, source_id, url, content_hash, price, price_basis (`month`, `night`, `week`, `stay`), query_checkin, query_checkout, `data` JSON, raw_path. **One row per listing per run, always**, so "seen in run N" is a fact in the table and a taken-down listing is distinguishable from an unchanged one. `content_hash` is the hash of the normalized parsed fields plus query dates (not the raw payload, whose image URLs expire); history views collapse consecutive rows with the same hash.
- `links`: id, ts, author (rule name or `user`), source, source_id, place_key, unit_key, reason. "This listing is this place." The current link for a listing is the newest `user` row if any, else the newest rule row; identity appends a rule row only when its decision differs from the current rule link.
- `trips`: id, computed_at, place_key, point_id (`set:name`), mode, minutes, distance_m, `legs` JSON, depart_assumption, provider.
- `checks`: id, ts, author, queue (`sample`, `conflict`, or `adhoc`, reserved for a future check control in the detail drawer; today checks are made in verify mode), observation_id or trip_id, field, stored_value (JSON), verdict (`correct`, `wrong`, `cannot_tell`), true_value (JSON), note. A `wrong` verdict's `true_value` overrides the scraped value in the derived views **only while the listing's latest observed value still equals `stored_value`**; once the source changes the value, the correction lapses and the new value is shown. The same rule defines *check state* everywhere (view `current_checks`: latest check per listing and field, valid while the value is unchanged), so a new run with the same value keeps a listing checked, and a changed value puts it back in the queues.
- `api_calls`: id, ts, provider, mode, ok, note. One row per paid routing call (see Google metering in the decision log).
- `media`: id, fetched_at, url, kind (`photo`, `plan`), status (HTTP status; 0 = network error), error, sha256, phash, same_as, distance, width, height, bytes, stored_bytes. One row per download attempt by `aptf-media fetch`, failures included. `sha256` and `phash` (64-bit pHash, hex) are of this download re-encoded; `width`, `height`, `bytes` of the original. `same_as` set: an exact or near copy of a file already stored for the same place, so nothing was written (`distance` = pHash bits apart, `stored_bytes` NULL); the URL is served from `COALESCE(same_as, sha256)`. New data (what we downloaded and stored), not a copy of an observation fact, so allowed as a log.
- `annotations`: id, ts, author, entity_type, entity_key, attribute (free text: `gym`, `walk_to_caltrain`, `living_room`, `overall`, `status`, ...), goal_id (optional), rating (1 to 5, optional), comment. The latest row per entity, attribute and author is the current value. Only the web app writes here.

### `observations.data` JSON

Parsed fields, all optional: `address`, `unit`, `city`, `zip`, `lat`, `lon`, `beds` (0 = studio; a private room is `beds = 1` with `kind = room`), `baths`, `sqft`, `kind` (`apartment`, `house`, `townhome`, `room`, `entire_place`), `term` (`long` or `short`), `furnished`, `private_bath`, `available_from`, `available_to`, `amenities` (list), `floor_plan`, `property_name`, `operator`, `title`, `description`, `media` (list of `data/media/` paths), `extra` (anything source-specific). One `extra` name is shared by every source: `floorplan_image`, the URL of the plan's or unit's floor plan drawing as the source gives it (Avalon `floorPlan.highResolution` on `resource.avalonbay.com`, Zumper plan media of type 2, Zillow `richMedia[].rmxData[].floorPlan.heroImageUrl`, Apartments.com `models[].imageLarge`, a render's page image whose label names the plan); absent when there is none. A `direct` `site_info` row may carry `plan_drawings`, {label: URL} (Prometheus' own plan-name map; on other sites the images whose alt, class or URL says floor plan, label = alt text plus file name), never read as plans.

### Derived views (never written)

`latest_obs`, `current_links`, `listings`, `units`, `places`, `operators`, `current_checks`, `field_overrides` and `obs_history` are SQL views over the logs, created by `store.init_db`. They are views, not tables, so there is no second copy to drift. If they get slow, they become materialized tables rebuilt by one `derive` command with no change to readers.

Goal outcomes are not stored at all: `filter.evaluate` computes them at read time from the views, `trips` and `config/goals.toml`, so changing a threshold takes effect on the next page load.

Keys are deterministic so annotations and trips survive any rebuild: `place_key` is a hash of the normalized street address (or of lat/lon rounded to 4 decimals when there is no address), `unit_key` adds the normalized unit or floor plan label, and a listing is `(source, source_id)`.

### Config (human-edited, read at startup)

Your own config is `config/`, gitignored: real goals, commute targets, hand-listed community sites (data gathering, not code) and `discovered_sites.toml` (append-only; a `[[check]]` carries an `outcome`: `ok`, `rejected` = fetched and the street address is not on the page, the only outcome that drops a site, or a retryable `blocked`, `timeout`, `error`, `not_fetched`, `empty`; the latest check of a site wins). `config.example/` is the committed template with the same files and anonymized values; it is used when `config/` does not exist (`settings.CONFIG_DIR`, override with `APTF_CONFIG`), and tests always use it. Paths below say `config/` for either.

- `config/goals.toml`: goal definitions as a list of typed rules per goal (hard rules and nice-to-haves), plus verification thresholds.
- `config/area.toml`: cities and bounding box.
- `config/points/*.csv`: one file per point set, columns `set,name,lat,lon` plus free columns. The single concept for anything a place can be near or travel to:
  - `commute_targets.csv`: Googleplex, Meta HQ, Downtown Palo Alto, Rengstorff industrial complex (1000 N Rengstorff Ave, Mountain View; a stand-in for a possible office).
  - `caltrain_stations.csv`: Redwood City, Menlo Park, Palo Alto, California Ave, San Antonio, Mountain View, Sunnyvale, Lawrence. Extra columns `service` (best tier that stops there: `express` or `local`), `patterns` and `other_transit`.
  - `grocery_chains.csv` (Walmart, Safeway, Whole Foods, Trader Joe's) and `grocery_any.csv` (every supermarket and grocery), generated once from OpenStreetMap by `scripts/osm_groceries.py` and committed.
  - `google_bus_stops.csv`: empty until the user supplies the list.
- `config/point_sets.toml`: per set, which modes to compute and how many nearest points to route to. "Proximity" is a query (the minimum walk `trips` row for a set), not a table.
- `config/caltrain.toml`: station-to-station ride times per service pattern and headways, used by the commute module's train legs.
- `config/media.toml`: `[media] max_gb` (default 5 when the file is missing), the hard cap on `data/media/` for `aptf-media fetch`.

## Components

All code lives in one Python package `aptfinder` (`src/aptfinder/`), one subpackage per component, each with its own CLI entry point (`aptf-<component>`) and tests under `tests/`.

### store (`aptf-db`)
- Goal: own the schema: log tables, append-only triggers, derived views; append helpers.
- Inputs: a database path.
- Outputs: an initialized SQLite file; `append_*` functions; `seed` command writing demo observations to `data/seed.db`.
- Must not: update or delete log rows; hold business rules beyond key derivation and view definitions.

### intake (`aptf-intake`)
- Goal: bring listings into `observations`, as wide as possible.
- Inputs: `config/area.toml`, source adapter configs, `APIFY_TOKEN`, spend cap.
- Outputs: `runs` rows, one `observations` row per listing per run, raw files under `data/raw/`, mirrored media under `data/media/`.
- Must not: filter by goal; scrape any listing site directly from this machine (Apify only); contact anyone; quietly accept empty or suspicious output (stop and ask the user).
- Tiers: aggregators discover places; direct enrichment reads a known place's own website (through an Apify web-scraping actor) for availability, per-unit pricing and floor plans, stored with `source = direct`; portfolio discovery follows an operator's "other properties" page. When direct and aggregator data disagree both are kept and direct is shown as current.
- **Areas** (`config/areas.toml`, `config.load_areas`): ZIP codes, cities and station boxes that the Caltrain stations' 25-minute walk zones (radius `radius_km`) touch, plus one `site` area per community website. Each adapter has an `area_kind` (zip, city, box or site) and covers every area of that kind: `aptf-intake run <source>` runs every area of its kind not covered yet, `--area` picks some. The coverage ledger (`intake.base.coverage`, `aptf-intake coverage`) is per (source, area), read from `runs.params.areas`. Steps that act on places (`discover-sites`, `promote-sites`, the own-site list, `compute --candidates`, the Pipeline's website and Google counts) take the places inside some station's walk zone (`areas.in_walk_zone`: within `radius_km` of a `[[box]]` station); `render` and `run direct` take every site in the list.
- No actor is assumed to work: each is chosen by running it for the area and comparing with the benchmark and manual checks. After each new source's first run, the user works a sample queue for it before it is relied on.
- **Google Places (`google_places`, `intake/places.py`)**: the official Places API (New) Text Search, called directly (an API, not a listing site), per station box (`[[box]]`; the box is the search's `locationRestriction`, so results stay inside the walk zone, unlike a city name). One request per query in `[google_places] queries` (text `apartments` with `includedType` `apartment_complex`, then `apartment_building`, strict type filtering) and page (20 results, at most 3 pages = 60; a query that fills all 3 marks its box partial; reaching a cap keeps what was fetched and marks the run's boxes partial). Field mask: id, displayName, formattedAddress, location, websiteUri, nationalPhoneNumber, rating, userRatingCount, businessStatus, types, primaryType, googleMapsUri. One fetch covers every box of a run (batch), so every request is checked against the run's `max_calls` across all boxes and `places_monthly_call_cap` (config/google.toml) and logged in `api_calls` as provider `places`, apart from Routes (`google`). Each place is one `site_info` row (source_id the place id, url its Google Maps page, `extra.website` / phone / rating / business status / types); permanently closed places are skipped. The intake base gained two hooks for it: an adapter's `fetch` replaces the Apify actor run (no Apify credit check when `apify = False`), and `skip` leaves items out on purpose (counted `skipped`, not `unparsed`).
- **Zumper and PadMapper (`zumper`, `padmapper`, `intake/zumper.py`)**: one inventory (Zumper owns PadMapper; the same listing ids appear on both), searched per city (`[[city]]`: the sites' URLs are per city, `zumper.com/apartments-for-rent/<city>-ca`, PadMapper's `<city>-ca` slug). Zumper through `scrapemind/zumperCom-Scraper` with `getDetails`: a building comes with its floor plans, and each plan on the market (status 1, with a price or an offered unit) is one row, source_id `plan:<plan listing id>` (the item's own id is only one of its plans), (plan name, beds, baths incl. half baths, sqft, lowest price, available date, units offered), plus the building's own website (`homepage`) as `extra.website`; a single unit or house is one row, its baths from `min_all_bathrooms` ([full, half], so full + half/2; `min_bathrooms` is the full count only), with `extra.baths_full`/`baths_half` on every Zumper row that has them. PadMapper through `bovi/padmapper-scraper`, search results only: a single unit is a row; a building summary spanning several bedroom counts is a `site_info` row `building:<building id>` (ranges in extra), never an offer with an invented price. Furnished stays (`lease_type` 10, or a Blueground provider or homepage) are short-term, furnished, operator Blueground where named, so identity gives them their own stay place; a stay operator's link is never the building's website. Items are attributed to the city they state (searches spill into nearby cities).
- **Operator portfolios (`portfolio`, `intake/portfolio.py`)**: each big landlord's own city page (URL templates per operator in `[portfolio] operators`, `{slug}` = city), all operator x city pages in one `apify/playwright-scraper` run (clicks 'load more' style buttons, never apply/tour/contact). One generic reader, no per-site parser: Haiku lists the communities shown (name, street, city, link from the page's link list), and the answer is stored in the raw item, so `reparse` re-checks it for free. Kept only as far as the page shows it: name on the page; street on the page; link exactly on the page and on the operator's host (else no link, and no operator: Avalon's page also lists an Equity community). Each community is a `site_info` row, source_id its link without scheme or query (one row for a community seen from two pages), `extra.website` its community page (a lead for `promote-sites`). A blocked (403/429/captcha) or missing page is unparsed, warned and makes the run's areas partial.
- **Own-site render (`aptf-intake render`, `intake/render.py`)**: each site in the list (Avalon excluded: its page data gives every unit) through `apify/playwright-scraper`. The page function clicks expanders, opens the community's floor-plans page and up to 5 per-plan unit lists per site ('View apartments', 'View units', 'Available units'): a link is opened as a page, a button without a link is clicked in place and the dialog it opens is read. Every page followed stays inside the start page's scope (origin + first path segment) and nothing that applies, tours, contacts, schedules or leases is ever clicked or opened. At most 7 pages a site (`maxRequestsPerCrawl`). Haiku reads a site's pages together, each cut to its own budget (start and floor-plans pages 12,000 characters, unit pages 6,000), so unit numbers, prices and dates reach it; a plan or unit counts only if its name, price and sqft are on the page. The page function also returns each page's images (src, alt, class); a plan's `floorplan_image` is one of them whose alt or file name names the plan (`plans.match_drawing`, exactly one), never a URL Haiku states. **Outcomes, failure vs not:** every render records per site, in the run's `counts.areas['<site>#render']`, an `outcome` beside the area `state`: `ok` (plans found; state `complete`), `no_plans` (rendered, nothing offered; state `empty`), or a transient failure with state `failed`, which retires nothing: `blocked` (HTTP 403/429 or the crawler's 'Request blocked'), `timeout`, `empty` (under 200 characters of text), `not_returned` (no item), `error` (any other request failure), `not_read` (Claude budget reached); with `http_status`, `error` (the scraper's message), pages and unit pages read and failed child pages. Failures come from the actor's failed-request items (`#error` / `#debug`, kept by fetching the dataset with `clean=false`), else from the run log, which the raw file keeps. A run over the whole site list (the default) picks transient failures first, then sites never rendered, then those older than 7 days; `ok` and `no_plans` are done until then. `--retry-failed` picks only the failures; `--site` always renders. Runs from before outcomes read their state (complete -> ok, empty -> no_plans, failed -> not_returned).
- **Text reading (`aptf-intake extract <source>|all`, `intake/extract.py`), a core phase.** Haiku (`claude -p`, no tools) reads the whole entry of every active listing of each text source (`TEXT_SOURCES`: craigslist, furnishedfinder, airbnb, apartments_com, zillow, zumper, padmapper) that has text (a description of 40+ characters or an amenity list, as stored). The entry is title, name, description, amenity list and source extras as stored, plus allowlisted fields of the listing's raw item for sources whose parser stores less (Apartments.com: about text, lease terms, one-time and monthly fees, included utilities, parking, pet and parking fees, amenity groups; Zumper: full and supplemental description, pet policy, fees, deposits, parking, specials, tags; Zillow: highlights and required monthly fees); the raw item is found by re-running the source's parser over `raw_path` (no reviews, schools, transit or other buildings). Unit-specific values are left out, so a building's units send the same text and are asked once; capped at 5,000 characters, 10 entries per call, `--workers` calls (default 8) in parallel, each a separate `claude -p`; the database and the cache are written only by the main thread; new calls stop once `--max-usd` is spent or any call is blocked (answers already paid for are applied, then the blocker is reported). Schema (version 2): address, building name and website (verbatim checks as before), and facts `{value, evidence}`: gym, pool, in-unit laundry, shared laundry, parking (garage / covered / lot / street / none), EV charging, air conditioning, dishwasher, cats allowed, dogs allowed, furnished, private bath, utilities included (which), minimum stay, lease months, application / admin / monthly fees. A fact counts only if its quote appears verbatim in the text sent (a fee's number must be in its quote); unknown stays null and absence is never inferred. The reading is a new observation of the listing: empty fields filled as before; positive facts added to `amenities` in plain words with the suffix '(read from text)' ('Gym / fitness center', 'Pool', 'In-unit laundry', 'Parking: garage', ...), so amenity rules and the place's pooled amenities use them; a listing with no amenity list and no positive fact keeps none (unknown); every checked fact with its quote in `extra.extracted.facts` (`extra.extracted.v` = 2). Answers are cached by schema version, model and text (`data/extract_cache.json`, merged under a lock, so parallel runs share it). **Hook:** `aptf-intake run <text source>` reads the run's rows right after it (each new scraped row supersedes the listing's reading; unchanged text is cached, free), `--no-extract` skips, `--workers` / `--extract-max-usd` apply; `reparse` applies cached readings only (no calls, so a reparse stays free).
- Untested leads carried over from the original brainstorm (`handoff.md`, Apify store listings, never run):

  | Source | Actor to try | Listed price | Caveats noted then |
  |---|---|---|---|
  | Zillow, Apartments.com, Realtor.com, Zumper, Redfin | `tri_angle/real-estate-aggregator` | from $1.50 / 1k | one call, deduped output; verify rental coverage per provider |
  | Property-manager sites (RentCafe, Entrata, RealPage, AppFolio, Buildium) | `housingfeed/rental-listings-api` | unknown | its pages disagree on whether Zillow and Apartments.com are included; low usage |

  For Airbnb, query with real check-in and check-out dates at least 28 days apart so the returned price is the monthly-discounted total (`price_basis = stay`, query dates recorded on the observation). Blueground has no known actor yet.

### identity (`aptf-identity`)
- Goal: decide which listings are the same place and unit.
- Inputs: `latest_obs`, `current_links`.
- Outputs: appended `links` rows (rules: `addr_unit` = normalized address plus unit; `geo_near_address` = a coordinate-only listing within 80 m of an address-keyed building (a property name or 3+ listings), never for Airbnb, whose pins are offset; `geo_beds_price` = lat/lon rounded to 4 decimals plus beds plus price otherwise).
- Must not: overrule a `user` link; append a row that repeats the current decision.

### commute (`aptf-commute`)
- Goal: minutes and legs from coordinate A to coordinate B by a mode. Fully independent: no imports from the rest of `aptfinder`, no knowledge of apartments, goals or the main schema.
- Inputs: two `(lat, lon)` pairs, a mode, a `LegSource`, a SQLite path for its cache, station list and train table (passed in by the caller).
- Outputs: `Trip(minutes, distance_m, legs, provider, approximate)`.
- `LegSource` answers "minutes from A to B by walk, bike, drive or transit". Implementations: `GoogleRoutesLegSource` (Routes API, `GOOGLE_MAPS_API_KEY`), `StraightLineLegSource` (haversine times a detour factor at a fixed speed; free, labelled `estimate`), and a fake for tests.
- Cache: the module owns one table, `commute_legs`, in the database path it is given, keyed on origin and destination rounded to 4 decimals, mode, departure assumption and provider. Every single leg goes through it; composed modes are built from cached legs, so station-to-workplace legs are fetched once ever and each new apartment costs only its own legs. Callers never manage cache state.
- Modes: `walk`, `bike`, `drive` (no traffic), `transit`, `bike_train_bike` (bike to each of the nearest k stations, in-train time from `config/caltrain.toml` plus half the headway as wait, bike from the far station; fastest kept), `bike_bus_bike` (Google transit route with walking legs re-timed as bike legs; labelled approximate). Both composed modes also consider biking the whole way, so they are never slower than plain bike.
- `nearest(origin, points, mode, k)`: shortlist by straight line, route to the top k.
- Wait at a station is half the peak gap between trains across all patterns (`peak_trains_per_hour`); `bike_bus_bike` adds the transfer/wait time Google's route includes beyond its step durations.
- Must not: read or write any table but `commute_legs`.
- **Glue (`aptfinder/trips.py`, CLI `aptf-commute`)** is the only code that joins commute with the store: `route` for an ad-hoc A to B, `compute` to append `trips` for places per `config/point_sets.toml`. The free estimate provider covers every place; a paid provider respects each set's `prefilter_km`, per-mode `max_km` and `auto` (point name to the modes Google routes by itself; missing means every mode) and routes the full `modes` table only on demand and a `--max-calls` cap per run, with calls and estimated cost logged in `runs`. A trip row is appended only when none exists for that place, point, mode and provider or its minutes changed.

### filter (`aptf-filter`)
- Goal: evaluate each goal over the derived views and `trips`.
- Inputs: `listings`, `places`, `trips`, `config/goals.toml`, per-source accuracy from verify.
- Outputs: per listing and goal, `pass`, `fail` (with reasons) or `needs_check` (naming the missing or untrusted field). A place's outcome is the best outcome among its listings, except that **the own website wins**: at a place whose own site currently prices an offer (an active `direct` row with a price, not `site_info`; `plans.own_site_places`), only those own-site rows decide the place, and other sources' listings there keep their result (`decides: false`), stay stored and shown as 'also listed', and nominate nothing for paid routing.
- Must not: write to the database; drop anything.

### verify (`aptf-verify`)
- Goal: measure data accuracy instead of assuming it.
- Sample queue: seeded random sample drawn evenly across sources (round robin, not proportional to volume); computed trips sampled the same way by provider and mode. Straight-line estimate trips are never sampled. A listing leaves the queue once checked and returns if a checked field's value changes. Accuracy counts one vote per (listing, field, checked value).
- Conflict queue: units with more than one source disagreeing on price, beds, baths, sqft or availability, compared over **active** listings only (a retired plan never makes a conflict), and never at a place whose own website prices an offer (the own site is the truth there; disagreements among other sources, cross-source or text, are moot). Shown first. A conflict at a place whose own site has not been rendered yet (a `direct` row exists, no `extra.platform = 'render'` row, site not Avalon: `verify.pending_render`) carries `pending_render` and a reason and goes last, after the text conflicts: the render will likely settle it. `verify.all_conflicts` gives that order.
- Own-site list (`verify.own_site_queue`): named buildings (`is_named_building`) inside a station walk zone (`areas.in_walk_zone`) whose own sites give no usable offer (no active priced `direct` row), one plain reason each, the first that applies: no website known; a site is a contact/tour/lead form; a site's address check failed; a site was read but gave no plans or prices; every site failed to load (blocked, timeout, empty, not returned); a website known but not checked yet. Each item lists every URL known for the building (`own_site_urls`: the site list, sites found by search or named by listings, URLs you added; listings' links to one host collapsed into one row) with its last render or address check outcome and date. An item leaves by itself once a site gives priced offers, or when you dismiss it (annotation `own_site`, until you add another URL) or say it has no website (annotation `website` = none). Adding a URL appends an annotation `website`; every such URL becomes a site of its own (`promote-sites`), beside any site the place already has, and shows at once as 'pending check'.
- `aptf-verify samples --source <s> --n 5 --seed N`: n random rows of one source (seeded, over its rows sorted by source_id, so the same seed picks the same rows on any copy), each with the page to open (Google Maps place, Zumper/PadMapper listing, operator community page) and every stored field, `(missing)` named, for checking by hand against screenshots.
- Outputs: `checks` rows from the dashboard; accuracy per source and field with sample size and a Wilson 95% interval; cross-source agreement rate.
- A source whose measured accuracy on a field is below the threshold in `goals.toml` (with at least the minimum sample) gets that field treated as `needs_check` by the filter.

### media (`aptf-media`, `aptfinder/media.py`)
- Goal: our own copy of every listing photo and floor-plan drawing, because image URLs change or vanish and some hosts refuse hotlinking. Downloads only image files at URLs observations already carry (`data.media`, `extra.images` as strings or `{url|src}`, drawings `extra.floorplan_image` / `extra.plan_image`), directly from the machine it runs on (AGENTS.md rule 6 exception). Run on the box: `nix run .#media -- fetch` (resumable: URLs stored OK are skipped; failures are retried only with `--retry-failed`; `--limit N` for a pilot), `nix run .#media -- status`.
- Store: each image re-encoded to JPEG, photos at most 800 px on the long side at quality 75, drawings 1,280 px at 80 so their text stays readable, never upscaled (EXIF orientation applied, transparency on white). Content-addressed: `data/media/<sha256[:2]>/<sha256>.jpg`, the name being the hash of the stored bytes.
- Deduplicated in the write path, from the first download: downloads run in threads (at most 4 per host, 0.25 s apart, 429/5xx/network errors retried with backoff; a host that refuses 20 in a row with 401/403 is skipped for the rest of the run), and one serial writer decides for each: the same bytes already stored -> `same_as` itself; else a stored file of the same place (the URL's place, or its listing before it has one) and kind within `PHOTO_MAX_DISTANCE` = 6 pHash bits (drawings: 0, only against drawings) -> `same_as` that file; else write. Whichever copy arrived first is the stored one; a larger later copy is not re-written (its original size is in its row, so the better source is derivable).
- Cap: before each write the running total of `stored_bytes` is checked against `max_gb`; at the cap the run stops and logs "media store full (5.0 GB)" (`runs.counts.full`, shown by the pipeline's Photos stage). So URLs go in priority order: active listings first, then places that pass or need a check on a goal, then drawings, then the first 12 photos of each listing, then the rest.
- Each run is a `runs` row (component `media`) with counts per outcome and host.
