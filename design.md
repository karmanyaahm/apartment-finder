# Apartment finder: design

Living document. Source of truth for architecture. Any change to behaviour, schema, config shape or a decision updates this file and appends to the [decision log](#decision-log) in the same commit (see `AGENTS.md`).

## Context

A personal tool that runs locally (SQLite plus files on disk, web app on `127.0.0.1`, later exposed through a Cloudflare tunnel). The search has two goals that stay separate but share one global candidate list. The main output is a map dashboard that takes manual comments, ratings and verification checks.

## Goals (`config/goals.toml`, edited in the dashboard)

The goals below are the committed example (`config.example/goals.toml`); the real ones live in the gitignored `config/`. `goals.toml` is only the seed: goals are edited, created and deleted in the dashboard, and each edit is an `annotations` row (`entity_type` goal, `entity_key` the goal id, attribute `definition`, `comment` the JSON `{label, rules, nice}`; a delete is `{"deleted": true}`, a tombstone). The effective set (`filter.goals.effective_goals`) is the file overlaid by the latest row per goal id: seed goals keep their order, new goals follow in the order first saved; `[verify]` always comes from the file. With no goal rows, the effective set is exactly the file.

| | Goal 1: `temp` | Goal 2: `lease` |
|---|---|---|
| What | Airbnb, Furnished Finder, Blueground or similar furnished stay for one person | Apartment or house for a group |
| Sizes | private room is fine; bathroom must be private | 3bd with 2 or more baths (3/2, 3/2.5, 3/3) |
| Dates | Dec 1, 2026 to Jan 1, 2027 | from about Jan 1, 2027; availability ignored for now |
| Hard filters | at most 8 min bike, or at most 25 min walk or transit, to downtown Palo Alto; private bathroom; furnished; at most $4,000 a month | under $2,500 per bedroom; long-term lease |
| Nice to have | none | at or under $2,000 per bedroom; gym; walk to Caltrain 20 min or less; Google bus stop nearby (list supplied later); living room size or total sqft |

## Principle: gather wide, filter late

- **Ingest takes everything in the area**, whatever its beds, baths or price. Goals are filters over stored data, so changing a threshold or adding a goal needs no new scrape.
- **Everything is timestamped and kept.** Each fact carries when it was observed and which source and run produced it. Nothing is overwritten or deleted.
- **Unknown never rejects.** Any filter whose input is missing passes the place with `needs_check` and names the missing field.
- **Filters report, they do not drop.** A failing place stays in the database and on the map (dimmed) with its fail reasons.
- **Paid routing is the one lazy step.** Straight-line distance is computed for everything for free. Google routing runs first for places passing a loose straight-line prefilter, and on demand for any other place from the dashboard.

Search area (`config/area.toml`): every city along Caltrain from Redwood City to Sunnyvale: Redwood City, North Fair Oaks, Atherton, Menlo Park, Palo Alto (including Stanford), Los Altos, Mountain View, Sunnyvale.

## Storage: logs are the truth, entities are derived

One SQLite file `data/apartments.db`, plus `data/raw/` (untouched scraper output, one JSON file per run and source) and `data/media/` (mirrored photos and floor plans named by content hash, because listing image URLs expire). `data/` is gitignored. Seed/demo data lives in a separate file, `data/seed.db`, so it never mixes with real observations.

### Append-only logs

Triggers reject UPDATE and DELETE on every log table. The only exception: a `runs` row may be updated once to close it out (`finished_at`, `counts`, `est_cost`, `status`, `error`) while its `finished_at` is still NULL; its identifying columns can never change.

- `runs`: id, started_at, finished_at, component, source, `params` JSON, `counts` JSON, est_cost, status (`running`, `ok`, `error`, `aborted`), error. `params.scope` is `full` (the whole area for that source; the default) or `targeted` (e.g. direct enrichment of one place). A listing is `active` when its latest observation is from, or newer than, its source's latest successful full run; targeted runs never mark anything inactive.
- `observations`: id, run_id, observed_at, source, source_id, url, content_hash, price, price_basis (`month`, `night`, `week`, `stay`), query_checkin, query_checkout, `data` JSON, raw_path. **One row per listing per run, always**, so "seen in run N" is a fact in the table and a taken-down listing is distinguishable from an unchanged one. `content_hash` is the hash of the normalized parsed fields plus query dates (not the raw payload, whose image URLs expire); history views collapse consecutive rows with the same hash.
- `links`: id, ts, author (rule name or `user`), source, source_id, place_key, unit_key, reason. "This listing is this place." The current link for a listing is the newest `user` row if any, else the newest rule row; identity appends a rule row only when its decision differs from the current rule link.
- `trips`: id, computed_at, place_key, point_id (`set:name`), mode, minutes, distance_m, `legs` JSON, depart_assumption, provider.
- `checks`: id, ts, author, queue (`sample`, `conflict`, or `adhoc`, reserved for a future check control in the detail drawer; today checks are made in verify mode), observation_id or trip_id, field, stored_value (JSON), verdict (`correct`, `wrong`, `cannot_tell`), true_value (JSON), note. A `wrong` verdict's `true_value` overrides the scraped value in the derived views **only while the listing's latest observed value still equals `stored_value`**; once the source changes the value, the correction lapses and the new value is shown. The same rule defines *check state* everywhere (view `current_checks`: latest check per listing and field, valid while the value is unchanged), so a new run with the same value keeps a listing checked, and a changed value puts it back in the queues.
- `api_calls`: id, ts, provider, mode, ok, note. One row per paid routing call (see Google metering in the decision log).
- `media`: id, fetched_at, url, kind (`photo`, `plan`), status (HTTP status; 0 = network error), error, sha256, phash, same_as, distance, width, height, bytes, stored_bytes. One row per download attempt by `aptf-media fetch`, failures included. `sha256` and `phash` (64-bit pHash, hex) are of this download re-encoded; `width`, `height`, `bytes` of the original. `same_as` set: an exact or near copy of a file already stored for the same place, so nothing was written (`distance` = pHash bits apart, `stored_bytes` NULL); the URL is served from `COALESCE(same_as, sha256)`. New data (what we downloaded and stored), not a copy of an observation fact, so allowed as a log.
- `annotations`: id, ts, author, entity_type, entity_key, attribute (free text: `gym`, `walk_to_caltrain`, `living_room`, `overall`, `status`, ...), goal_id (optional), rating (1 to 5, optional), comment. The latest row per entity, attribute and author is the current value. Only the web app writes here.

### `observations.data` JSON

Parsed fields, all optional: `address`, `unit`, `city`, `zip`, `lat`, `lon`, `beds` (0 = studio; a private room is `beds = 1` with `kind = room`), `baths`, `sqft`, `kind` (`apartment`, `house`, `townhome`, `room`, `entire_place`), `term` (`long` or `short`), `furnished`, `private_bath`, `available_from`, `available_to`, `amenities` (list), `floor_plan`, `property_name`, `operator`, `title`, `description`, `media` (list of `data/media/` paths), `extra` (anything source-specific). One `extra` name is shared by every source: `floorplan_image`, the URL of the plan's or unit's floor plan drawing as the source gives it (Avalon `floorPlan.highResolution` on `resource.avalonbay.com`, Zumper plan media of type 2, Zillow `richMedia[].rmxData[].floorPlan.heroImageUrl`, Apartments.com `models[].imageLarge`, a render's page image whose label names the plan); absent when there is none. A `direct` `site_info` row may carry `plan_drawings`, {label: URL} (Prometheus' own plan-name map; on other sites the images whose alt, class or URL says floor plan, label = alt text plus file name), never read as plans.

### Derived views (never written)

`latest_obs`, `current_links`, `listings`, `units`, `places`, `operators`, `current_checks`, `field_overrides` and `obs_history` are SQL views over the logs, created by `store.init_db`. They are views, not tables, so there is no second copy to drift. If they get slow, they become materialized tables rebuilt by one `derive` command with no change to readers.

Goal outcomes are not stored at all: `filter.evaluate` computes them at read time from the views, `trips` and the effective goal set (`goals.toml` plus goal edits), so changing a threshold takes effect on the next page load.

Keys are deterministic so annotations and trips survive any rebuild: `place_key` is a hash of the normalized street address (or of lat/lon rounded to 4 decimals when there is no address), `unit_key` adds the normalized unit or floor plan label, and a listing is `(source, source_id)`.

### Config (human-edited, read at startup)

Your own config is `config/`, gitignored: real goals, commute targets, hand-listed community sites (data gathering, not code) and `discovered_sites.toml` (append-only; a `[[check]]` carries an `outcome`: `ok`, `rejected` = fetched and the street address is not on the page, the only outcome that drops a site, or a retryable `blocked`, `timeout`, `error`, `not_fetched`, `empty`; the latest check of a site wins). `config.example/` is the committed template with the same files and anonymized values; it is used when `config/` does not exist (`settings.CONFIG_DIR`, override with `APTF_CONFIG`), and tests always use it. Paths below say `config/` for either.

- `config/goals.toml`: the seed goal definitions as a list of typed rules per goal (hard rules and nice-to-haves), plus verification thresholds. Rule types (`filter.rules.RULE_TYPES`, checked by `validate_rule` before any dashboard edit is stored): `max` / `min` (numeric field, value, strict?), `equals` (term, furnished, private_bath, kind), `size_options`, `dates_cover`, `commute_any` (a point, `{mode, max}` options), `near` (a point set, mode, max), `amenity` (name, match words, exclude words), `known` (field), `net_commute` (agg = total, mean, median or spread, max minutes: the goal's hard commute rules combined, see the web section).
- `config/area.toml`: cities and bounding box.
- `config/points/*.csv`: one file per point set, columns `set,name,lat,lon` plus free columns. The single concept for anything a place can be near or travel to:
  - `commute_targets.csv`: Googleplex, Meta HQ, Downtown Palo Alto, Rengstorff industrial complex (1000 N Rengstorff Ave, Mountain View; a stand-in for a possible office).
  - `caltrain_stations.csv`: Redwood City, Menlo Park, Palo Alto, California Ave, San Antonio, Mountain View, Sunnyvale, Lawrence. Extra columns `service` (best tier that stops there: `express` or `local`), `patterns` and `other_transit`.
  - `grocery_chains.csv` (Walmart, Safeway, Whole Foods, Trader Joe's) and `grocery_any.csv` (every supermarket and grocery), generated once from OpenStreetMap by `scripts/osm_groceries.py` and committed.
  - `google_bus_stops.csv`: empty until the user supplies the list.
- `config/point_sets.toml`: per set, which modes to compute and how many nearest points to route to. "Proximity" is a query (the minimum walk `trips` row for a set), not a table.
- `config/caltrain.toml`: station-to-station ride times per service pattern and headways, used by the commute module's train legs.
- `config/media.toml`: `[media] max_gb` (default 5 when the file is missing), the hard cap on `data/media/` for `aptf-media fetch`.

## Components

All code lives in one Python package `aptfinder` (`src/aptfinder/`), one subpackage per component, each with its own CLI entry point (`aptf-<component>`) and tests under `tests/`.

### store (`aptf-db`)
- Goal: own the schema: log tables, append-only triggers, derived views; append helpers.
- Inputs: a database path.
- Outputs: an initialized SQLite file; `append_*` functions; `seed` command writing demo observations to `data/seed.db`.
- Must not: update or delete log rows; hold business rules beyond key derivation and view definitions.
- **Write transactions are short.** SQLite has one writer at a time, so every writer keeps its transactions short: bulk appends (intake runs, `reparse`, the extract apply step, identity links) commit every `store.COMMIT_EVERY` (200) rows; `render` commits each site's rows before the next site's Claude call; `aptf-media fetch` commits each row before waiting for the next download; nothing holds a pending write across a network, Apify or Claude wait. Partial progress is visible (the logs are append-only), and a run that fails is still closed as `error`. Connections wait up to 5 minutes for the lock (`store.connect`, and the commute leg cache). `store.begin_write(conn, on_wait)` takes the lock explicitly and reports that it is waiting; the dashboard's compute job uses it to show "waiting for the database (another job is writing)".

### intake (`aptf-intake`)
- Goal: bring listings into `observations`, as wide as possible.
- Inputs: `config/area.toml`, source adapter configs, `APIFY_TOKEN`, spend cap.
- Outputs: `runs` rows, one `observations` row per listing per run, raw files under `data/raw/`, mirrored media under `data/media/`.
- Must not: filter by goal; scrape any listing site directly from this machine (Apify only; the exceptions are the own-site precheck, a DNS lookup and one plain GET per site that reads a few KB and stores nothing of the page, and Prometheus's availability JSON, one request per Prometheus site, below); contact anyone; quietly accept empty or suspicious output (stop and ask the user).
- Tiers: aggregators discover places; direct enrichment reads a known place's own website (through an Apify web-scraping actor) for availability, per-unit pricing and floor plans, stored with `source = direct`; portfolio discovery follows an operator's "other properties" page. When direct and aggregator data disagree both are kept and direct is shown as current.
- **Areas** (`config/areas.toml`, `config.load_areas`): ZIP codes, cities and station boxes that the Caltrain stations' 25-minute walk zones (radius `radius_km`) touch, plus one `site` area per community website. Each adapter has an `area_kind` (zip, city, box or site) and covers every area of that kind: `aptf-intake run <source>` runs every area of its kind not covered yet, `--area` picks some. The coverage ledger (`intake.base.coverage`, `aptf-intake coverage`) is per (source, area), read from `runs.params.areas`. Steps that act on places (`discover-sites`, `promote-sites`, the own-site list, `compute --candidates`, the Pipeline's website and Google counts) take the places inside some station's walk zone (`areas.in_walk_zone`: within `radius_km` of a `[[box]]` station); `render` and `run direct` take every site in the list.
- No actor is assumed to work: each is chosen by running it for the area and comparing with the benchmark and manual checks. After each new source's first run, the user works a sample queue for it before it is relied on.
- **A price of 0 or less is unknown.** Every parser's `Parsed` turns it into NULL, so it never becomes a $0 rent, $0 per bed or the place's minimum; goals report `needs_check` (price unknown). `reparse` tags each row with its intake area (`extra.area`) exactly as the original run did, so later complete area runs can still retire it.
- **Google Places (`google_places`, `intake/places.py`)**: the official Places API (New) Text Search, called directly (an API, not a listing site), per station box (`[[box]]`; the box is the search's `locationRestriction`, so results stay inside the walk zone, unlike a city name). One request per query in `[google_places] queries` (text `apartments` with `includedType` `apartment_complex`, then `apartment_building`, strict type filtering) and page (20 results, at most 3 pages = 60; a query that fills all 3 marks its box partial; reaching a cap keeps what was fetched and marks the run's boxes partial). Field mask: id, displayName, formattedAddress, location, websiteUri, nationalPhoneNumber, rating, userRatingCount, businessStatus, types, primaryType, googleMapsUri. One fetch covers every box of a run (batch), so every request is checked against the run's `max_calls` across all boxes and `places_monthly_call_cap` (config/google.toml) and logged in `api_calls` as provider `places`, apart from Routes (`google`). Each place is one `site_info` row (source_id the place id, url its Google Maps page, `extra.website` / phone / rating / business status / types); permanently closed places are skipped. The intake base gained two hooks for it: an adapter's `fetch` replaces the Apify actor run (no Apify credit check when `apify = False`), and `skip` leaves items out on purpose (counted `skipped`, not `unparsed`).
- **Zumper and PadMapper (`zumper`, `padmapper`, `intake/zumper.py`)**: one inventory (Zumper owns PadMapper; the same listing ids appear on both), searched per city (`[[city]]`: the sites' URLs are per city, `zumper.com/apartments-for-rent/<city>-ca`, PadMapper's `<city>-ca` slug). Zumper through `scrapemind/zumperCom-Scraper` with `getDetails`: a building comes with its floor plans, and each plan on the market (status 1, with a price or an offered unit) is one row, source_id `plan:<plan listing id>` (the item's own id is only one of its plans), (plan name, beds, baths incl. half baths, sqft, lowest price, available date, units offered), plus the building's own website (`homepage`) as `extra.website`; a single unit or house is one row, its baths from `min_all_bathrooms` ([full, half], so full + half/2; `min_bathrooms` is the full count only), with `extra.baths_full`/`baths_half` on every Zumper row that has them. PadMapper through `bovi/padmapper-scraper`, search results only: a single unit is a row; a building summary spanning several bedroom counts is a `site_info` row `building:<building id>` (ranges in extra), never an offer with an invented price. Furnished stays (`lease_type` 10, or a Blueground provider or homepage) are short-term, furnished, operator Blueground where named, so identity gives them their own stay place; a stay operator's link is never the building's website. Items are attributed to the city they state (searches spill into nearby cities). **PadMapper is skipped** (`skip = true` in its `sources.toml` section, since 2026-11-25): it adds nothing Zumper lacks, so `run padmapper` refuses and coverage and the pipeline leave it out; its stored rows stay. Any source can be skipped the same way.
- **RentCafe (`rentcafe`, `intake/rentcafe.py`)**: Yardi's listing site, searched per city (`[[city]]`, location `<city>, CA`, one actor run per city) through `benthepythondev/rentcafe-apartments-scraper` with property details: the actor pages through the whole city search (50 properties a page, until a short page) and opens each property for its floor plans; `siteTotal` (raw file only, not on rows, so a moving count never changes row hashes) is the site's count of rentals, i.e. units, not properties (Mountain View: 462 rentals in 72 properties). Each floor plan with a rent is one row, source_id `plan:<floorPlanId>` (name, beds, baths, sqft, lowest rent as a monthly price, `plan_price_max`, `plan_available` = units available now, `rent_text`); a property whose plans all say "Ask for pricing" is one `site_info` row `building:<propertyId>`, never an offer. Extra: property id, rent and bed ranges, total units, the current special, application and pet fees, cats/dogs, year built. Every item links its rentcafe.com page, an aggregator page (`AGGREGATOR_HOSTS`), so `extra.website` stays empty unless a link leads off rentcafe.com (a rentcafewebsite.com community site would be kept). The search spills into neighbouring cities; an item counts for the city it states. Not given by this actor: the card's "Base rent" vs "Total monthly leasing price" label and the units-available count (see the decision log).
- **Zillow detail pages (`aptf-intake zillow-detail`, `intake/zillow_detail.py`)**: an enrichment of Zillow listings already held, not a listing source. One page per zpid of the active Zillow listings without a page yet (a building's bedroom rows `<zpid>:Nbd` share one; `--refetch` takes all), through `delicious_zebu/zillow-property-details-scraper` (input `{"zpids": [...]}`), 150 zpids per actor run (a timeout loses one batch), the budget guard (`base.spend_room`, shared with `run_source`: run cap and Apify credit minus `spend.reserve_usd`) before each run, `--max-usd` required. Raw pages only, `data/raw/zillow_detail/run<id>_<k>.json`: no observations, so no listing, place or geocode; one `runs` row (component intake, source `zillow_detail`, `scope = targeted`), not in `ADAPTERS`, so never coverage and never retiring anything. Items are keyed by `zillow_id` (their `zpid` is empty); requested minus returned are `failed`. A building zpid returns one representative unit's page: its beds, baths, price, dates and deposit are never read. The run's `counts.home_status` maps each page's zpid to its `home_status` and `counts.last_event` gives a non-rental page's newest price-history event; an explicit non-rental status (anything but FOR_RENT) puts the listing in Verify (`verify.stale_queue`).
- **Operator portfolios (`portfolio`, `intake/portfolio.py`)**: each big landlord's own city page (URL templates per operator in `[portfolio] operators`, `{slug}` = city), all operator x city pages in one `apify/playwright-scraper` run (clicks 'load more' style buttons, never apply/tour/contact). One generic reader, no per-site parser: Haiku lists the communities shown (name, street, city, link from the page's link list), and the answer is stored in the raw item, so `reparse` re-checks it for free. Kept only as far as the page shows it: name on the page; street on the page; link exactly on the page and on the operator's host (else no link, and no operator: Avalon's page also lists an Equity community). Each community is a `site_info` row, source_id its link without scheme or query (one row for a community seen from two pages), `extra.website` its community page (a lead for `promote-sites`). A blocked (403/429/captcha) or missing page is unparsed, warned and makes the run's areas partial.
- **Own-site render (`aptf-intake render`, `intake/render.py`)**: each site in the list (Avalon excluded: its page data gives every unit; Prometheus excluded: read from its availability JSON, below) through `apify/playwright-scraper`. The page function clicks expanders, opens the community's floor-plans page and up to 5 per-plan unit lists per site ('View apartments', 'View units', 'Available units'): a link is opened as a page, a button without a link is clicked in place and the dialog it opens is read. Every page followed stays inside the start page's scope (origin + first path segment) and nothing that applies, tours, contacts, schedules or leases is ever clicked or opened. At most 7 pages a site (`maxRequestsPerCrawl`). Haiku reads a site's pages together, each cut to its own budget (start and floor-plans pages 12,000 characters, unit pages 6,000), so unit numbers, prices and dates reach it; a plan or unit counts only if its name, price and sqft are on the page. The page function also returns each page's images (src, alt, class); a plan's `floorplan_image` is one of them whose alt or file name names the plan (`plans.match_drawing`, exactly one), never a URL Haiku states. **Outcomes, failure vs not:** every render records per site, in the run's `counts.areas['<site>#render']`, an `outcome` beside the area `state`: `ok` (plans found; state `complete`), `no_plans` (rendered, nothing offered; state `empty`), or a transient failure with state `failed`, which retires nothing: `blocked` (HTTP 403/429 or the crawler's 'Request blocked'), `timeout`, `empty` (under 200 characters of text), `not_returned` (no item), `error` (any other request failure), `not_read` (Claude budget reached); with `http_status`, `error` (the scraper's message), pages and unit pages read and failed child pages. Failures come from the actor's failed-request items (`#error` / `#debug`, kept by fetching the dataset with `clean=false`), else from the run log, which the raw file keeps. A run over the whole site list (the default) picks transient failures first, then sites never rendered, then those older than 7 days; `ok` and `no_plans` are done until then. `--retry-failed` picks only the failures; `--site` always renders. Runs from before outcomes read their state (complete -> ok, empty -> no_plans, failed -> not_returned). **Precheck (`intake/precheck.py`, before every render and every `promote-sites` fetch, free):** per site a DNS lookup of the host and one plain GET from this machine (browser User-Agent, redirects followed, 12 s timeout, at most 16 KB of the body read, nothing stored). `dead`: the host does not resolve (`EAI_NONAME`/`EAI_NODATA`: NXDOMAIN, or a CNAME to nothing). `challenge`: a Cloudflare bot challenge to the plain GET (header `cf-mitigated: challenge`, or `server: cloudflare` with a 403/429/503 whose first bytes carry 'Just a moment...' / `cf-chl` / `challenge-platform`): reported by `aptf-intake precheck`, never recorded or skipped, because Apify's browser gets through (see the decision log). Anything else proceeds as before, including a temporary DNS failure, a timeout, a TLS error, a bare 403 and a malformed host (spaces in it). Only a `dead` site is not sent to Apify (`config.PRECHECK_SKIP`): render records it as its outcome (state `failed`, retires nothing; label 'site dead (DNS)'), `promote-sites` as a `[[check]]` with that outcome (not in `CHECK_RETRY`, never a rejection). Neither `--retry-failed` takes it; a plain `render` / `promote-sites` takes it again once the outcome is over 7 days old, and the fresh precheck decides; `render --site` takes it at once, still gated by the fresh precheck. `aptf-intake precheck [--site ID] [--dry-run]` checks every site in the list and records only `dead` (one `runs` row, `params.render` + `precheck`, scope `targeted`, cost 0; plus a `[[check]]` for a discovered site whose address check is not ok), so it never overwrites a real render outcome.
- **Prometheus availability JSON (`aptf-intake prometheus [--site ID]`, `intake/prometheus.py`)**: the sites in the list whose platform is `prometheus`, read directly from the machine it runs on (AGENTS.md rule 6 exception, 2026-11-25), one request per site, sequential, 2 s apart, a normal browser UA: `https://shopping.prometheusapartments-prod-west2.com/<id>/available-units?date=<today>`, a JSON list of the units offered (plan name, `rent` and `bestRent` for `bestTerm` months, sqft, beds, baths, unit and building number, ready date, deposit, hold status). `<id>` is the community page's `__NEXT_DATA__` -> `props.pageProps.apartmentPageData.id`, taken from the site's stored `direct` raw file (its `<site>:site` row), else from the page fetched once, and cached in `data/prometheus_ids.json`. Each unit is one row: source `direct`, source_id `<site>:r:<unit>` (render's scheme; `<building>-<unit>` when a building number is given), price `bestRent` (else `rent`) per month, `floor_plan`, unit, beds, baths, sqft, `available_from` the ready date, `operator` Prometheus, extra `platform` 'render' with `reader` 'prometheus_json' (so Verify's pending-render check and the render outcomes treat it as rendered), `area` `<site>#render`, rent, best rent and term, deposit, floor, plan and unit ids, `on_hold`, and `floorplan_image` from the site row's `plan_drawings` when a key equals the plan name (else `plans.match_drawing`). The run is logged like a render (component intake, source `direct`, `params.render`, `reader`, `scope` partial; `counts.areas['<site>#render']` with an outcome, units, plans and price range), so a list retires that site's older render rows (an empty list is `no_plans`, state empty, and retires them too), and a refused request (HTTP 403/429, or a JSON error such as Cloudflare's `challenge`) is `blocked` (state failed) and retires nothing; other failures are `error` or `timeout`, and so is a non-empty list that gives no rows (units without a unit number: a changed format, never read as 'nothing offered'). Sites sharing one community id (two list entries for one building) are asked once per run. Raw responses: `data/raw/direct/run<id>_prometheus_json.json`. No Apify, no Claude, $0. The pipeline suggests `aptf-intake prometheus` when a Prometheus site was never read, failed, or is older than 7 days, and `render` only for the other sites.
- **Text reading (`aptf-intake extract <source>|all`, `intake/extract.py`), a core phase.** Haiku (`claude -p`, no tools) reads the whole entry of every active listing of each text source (`TEXT_SOURCES`: craigslist, furnishedfinder, airbnb, apartments_com, zillow, zumper, padmapper) that has text (a description of 40+ characters, an amenity list or Zillow's required monthly fees, as stored). The entry is title, name, description, amenity list and source extras as stored (pets, laundry, housing type, Zillow's `required_monthly_fees`), plus allowlisted fields of the listing's raw item for sources whose parser stores less (Apartments.com: about text, lease terms, one-time and monthly fees, included utilities, parking, pet and parking fees, amenity groups; Zumper: full and supplemental description, pet policy, fees, deposits, parking, specials, tags); the raw item is found by re-running the source's parser over `raw_path` (no reviews, schools, transit or other buildings). Zillow: the listing's newest detail page, found by `extra.zpid` (`zillow_detail.load_pages`): description, what's special, and plain lines of fees by type (not the deposit), allowed pets, laundry, appliances, cooling, parking, community features, association amenities, pool, utilities, lease term, and 'Furnished: yes' only when true (false is on nearly every page, a default); placeholders ('Contact For Details') are dropped. A Zillow listing with a page counts as having text. Unit-specific values are left out, so a building's units send the same text and are asked once; capped at 5,000 characters, 10 entries per call, `--workers` calls (default 8) in parallel, each a separate `claude -p`; the database and the cache are written only by the main thread; new calls stop once `--max-usd` is spent or any call is blocked (answers already paid for are applied, then the blocker is reported). Schema (version 2): address, building name and website (verbatim checks as before), and facts `{value, evidence}`: gym, pool, in-unit laundry, shared laundry, parking (garage / covered / lot / street / none), EV charging, air conditioning, dishwasher, cats allowed, dogs allowed, furnished, private bath, utilities included (which), minimum stay, lease months, application / admin / monthly fees. A fact counts only if its quote appears verbatim in the text sent (a fee's number must be in its quote); unknown stays null and absence is never inferred. The reading is a new observation of the listing: empty fields filled as before; positive facts added to `amenities` in plain words with the suffix '(read from text)' ('Gym / fitness center', 'Pool', 'In-unit laundry', 'Parking: garage', ...), so amenity rules and the place's pooled amenities use them; a listing with no amenity list and no positive fact keeps none (unknown); every checked fact with its quote in `extra.extracted.facts` (`extra.extracted.v` = 2). Answers are cached by schema version, model and text (`data/extract_cache.json`, merged under a lock, so parallel runs share it). **Hook:** `aptf-intake run <text source>` reads the run's rows right after it (each new scraped row supersedes the listing's reading; unchanged text is cached, free), `--no-extract` skips, `--workers` / `--extract-max-usd` apply; `reparse` applies cached readings only (no calls, so a reparse stays free). **Free follow-up (same hook, `after_intake` -> `after_steps`):** after any `run` or `reparse` that wrote rows, of any source, and after the reading (even when the reading is blocked): geocode the address strings not in `data/geocode_cache.json` (`identity.addresses.geocode`, its run and monthly caps; skipped with a note when `GOOGLE_MAPS_API_KEY` is unset; never on `reparse`, which stays call-free), rebuild identity (an `identity` run; the only rebuild of a CLI `run` or `reparse`, which with `--no-followup` leave identity for the next one), then straight-line estimates (`trips.estimate_missing`, a `commute`/`estimate` run) for the routable places with no estimate under the current point ids, the Pipeline panel's rule; places that have estimates are not routed again. One summary line, e.g. `after intake: geocoded 12 (cached 340), identity rebuilt (16 links), estimates for 9 new places (279 trips)`. `--no-followup` skips the three steps.

### identity (`aptf-identity`)
- Goal: decide which listings are the same place and unit.
- Inputs: `latest_obs`, `current_links`.
- Outputs: appended `links` rows (rules: `addr_unit` = normalized address plus unit; `geo_near_address` = a coordinate-only listing within 80 m of an address-keyed building (a property name or 3+ listings), never for Airbnb, whose pins are offset; `geo_beds_price` = lat/lon rounded to 4 decimals plus beds plus price otherwise).
- Must not: overrule a `user` link; append a row that repeats the current decision.

### commute (`aptf-commute`)
- Goal: minutes and legs from coordinate A to coordinate B by a mode. Fully independent: no imports from the rest of `aptfinder`, no knowledge of apartments, goals or the main schema.
- Inputs: two `(lat, lon)` pairs, a mode, a `LegSource`, a SQLite path for its cache, station list and train table (passed in by the caller).
- Outputs: `Trip(minutes, distance_m, legs, provider, approximate)`.
- `LegSource` answers "minutes from A to B by walk, bike, drive or transit". Implementations: `GoogleRoutesLegSource` (Routes API, `GOOGLE_MAPS_API_KEY`), `StraightLineLegSource` (haversine times a detour factor at a fixed speed; free, labelled `estimate`), and a fake for tests.
- Cache: the module owns one table, `commute_legs`, in the database path it is given, keyed on origin and destination rounded to 4 decimals, mode, departure assumption and provider. Every single leg goes through it; composed modes are built from cached legs, so station-to-workplace legs are fetched once ever and each new apartment costs only its own legs. Callers never manage cache state.
- Modes: `walk`, `bike`, `drive` (no traffic), `transit`, `bike_train_bike` (bike to each of the nearest k stations, in-train time from `config/caltrain.toml` plus half the headway as wait, bike from the far station; fastest kept), `bike_bus_bike` (Google transit route with walking legs re-timed as bike legs; labelled approximate). Both composed modes also consider biking the whole way, so they are never slower than plain bike.
- `nearest(origin, points, mode, k)`: shortlist by straight line, route to the top k.
- Wait at a station is half the peak gap between trains across all patterns (`peak_trains_per_hour`); `bike_bus_bike` adds the transfer/wait time Google's route includes beyond its step durations.
- Must not: read or write any table but `commute_legs`.
- **Glue (`aptfinder/trips.py`, CLI `aptf-commute`)** is the only code that joins commute with the store: `route` for an ad-hoc A to B, `compute` to append `trips` for places per `config/point_sets.toml`. The free estimate provider covers every place; a paid provider respects each set's `prefilter_km`, per-mode `max_km` and `auto` (point name to the modes Google routes by itself; missing means every mode) and routes the full `modes` table only on demand and a `--max-calls` cap per run, with calls and estimated cost logged in `runs`. A trip row is appended only when none exists for that place, point, mode and provider or its minutes changed.

### filter (`aptf-filter`)
- Goal: evaluate each goal over the derived views and `trips`.
- Inputs: `listings`, `places`, `trips`, the effective goal set (`config/goals.toml` overlaid by goal annotations, `filter.goals`), per-source accuracy from verify. `goal_inputs` reads everything once; `evaluate_goal` judges one goal over it (`evaluate_all` runs it per goal; the dashboard's draft preview runs it on one unsaved goal).
- Outputs: per listing and goal, `pass`, `fail` (with reasons) or `needs_check` (naming the missing or untrusted field). A place's outcome is the best outcome among its listings, except that **the own website wins**: at a place whose own site currently prices an offer (an active `direct` row with a price, not `site_info`; `plans.own_site_places`), only those own-site rows decide the place, and other sources' listings there keep their result (`decides: false`), stay stored and shown as 'also listed', and nominate nothing for paid routing.
- Must not: write to the database; drop anything.

### verify (`aptf-verify`)
- Goal: measure data accuracy instead of assuming it.
- Sample queue: seeded random sample drawn evenly across sources (round robin, not proportional to volume); computed trips sampled the same way by provider and mode. Straight-line estimate trips are never sampled. A listing leaves the queue once checked and returns if a checked field's value changes. Accuracy counts one vote per (listing, field, checked value).
- Conflict queue: units with more than one source disagreeing on price, beds, baths, sqft or availability, compared over **active** listings only (a retired plan never makes a conflict), and never at a place whose own website prices an offer (the own site is the truth there; disagreements among other sources, cross-source or text, are moot). Shown first. A conflict at a place whose own site has not been rendered yet (a `direct` row exists, no `extra.platform = 'render'` row, site not Avalon: `verify.pending_render`) carries `pending_render` and a reason and goes last, after the text conflicts: the render will likely settle it. `verify.all_conflicts` gives that order.
- Too-cheap listings (`verify.cheap_queue`): an active, priced, monthly lease listing (not `term = short`, not `kind = room`, beds known) whose price per bedroom is below `[verify] min_price_per_bed` (default $1,000; a studio counts as 1 bedroom) is a one-listing conflict tagged `cheap`, with the reason 'price per bedroom $320 < $1,000: check for per-room or misread price', lowest $/bed first, after the text conflicts and before the pending ones. Furnished long leases are included. It shows price (to check) and beds (optional: a wrong beds corrects $/bed through the override); it leaves once the price has a current check (right: the price is real; wrong: the true monthly rent overrides it). Counted with the conflicts.
- No longer for rent (`verify.stale_queue`): an active Zillow listing whose newest detail page (see intake) states a non-rental `home_status` (FOR_SALE, SOLD, OFF_MARKET, ...) is a one-listing conflict tagged `stale` ('Zillow's page now says for sale, not for rent (latest: 2026-11-24 Price change $6,800): still offered?', the page's newest price-history event), after the too-cheap ones, on the price: ✓ still offered at it, ✗ or ? if gone. It leaves once the price has a current check or a newer page says FOR_RENT; a page with no status flags nothing. Nothing is retired automatically.
- Duplicate-building list (`verify.duplicate_queue`): pairs of places that are probably one building, each with its reasons, strongest first (own website 3, address 2, name 2, summed; then nearest): **similar address** (`identity.addresses.suspected_duplicates`: same street number, street names 85%+ alike, within 150 m); **same own website** (host and path, lowercase, no www., query or trailing slash: the site list or a site search found for the place (a failed address check rules one out), a `direct` site scraped at both, or the website a listing names; within 600 m; a URL shared by more than 6 places is a manager's site and ignored); **same name** (property name without 'the', 'apartments' and the like, not starting with a digit, within 200 m). Third-party stay places (`~`) and places you split off (`u_`) are left out. Bucketed by street number, URL and name, never all pairs (0.7 s on 2,718 places, plus the cached places view). A pair leaves by itself after a merge (one place is gone) or when you answer 'not the same building' (annotation `place_pair` / `<a>|<b>` sorted / `same_building` = no).
- Own-site list (`verify.own_site_queue`): named buildings (`is_named_building`) inside a station walk zone (`areas.in_walk_zone`) whose own sites give no usable offer (no active priced `direct` row), one plain reason each, the first that applies: no website known; a site is a contact/tour/lead form; a site's address check failed; a site was read but gave no plans or prices; a site's domain is dead (DNS, from the precheck); every site failed to load (blocked, timeout, empty, not returned); a website known but not checked yet. Each item lists every URL known for the building (`own_site_urls`: the site list, sites found by search or named by listings, URLs you added; listings' links to one host collapsed into one row) with its last render or address check outcome and date. An item leaves by itself once a site gives priced offers, or when you dismiss it (annotation `own_site`, until you add another URL) or say it has no website (annotation `website` = none). Adding a URL appends an annotation `website`; every such URL becomes a site of its own (`promote-sites`), beside any site the place already has, and shows at once as 'pending check'.
- `aptf-verify samples --source <s> --n 5 --seed N`: n random rows of one source (seeded, over its rows sorted by source_id, so the same seed picks the same rows on any copy), each with the page to open (Google Maps place, Zumper/PadMapper listing, operator community page) and every stored field, `(missing)` named, for checking by hand against screenshots.
- Outputs: `checks` rows from the dashboard; accuracy per source and field with sample size and a Wilson 95% interval; cross-source agreement rate.
- A source whose measured accuracy on a field is below the threshold in `goals.toml` (with at least the minimum sample) gets that field treated as `needs_check` by the filter.

### media (`aptf-media`, `aptfinder/media.py`)
- Goal: our own copy of every listing photo and floor-plan drawing, because image URLs change or vanish and some hosts refuse hotlinking. Downloads only image files at URLs observations already carry (`data.media`, `extra.images` as strings or `{url|src}`, drawings `extra.floorplan_image` / `extra.plan_image` / the URLs of own-site `extra.plan_drawings`), directly from the machine it runs on (AGENTS.md rule 6 exception). Run on the box: `nix run .#media -- fetch` (resumable: URLs stored OK are skipped; failures are retried only with `--retry-failed`; `--limit N` for a pilot), `nix run .#media -- status`.
- Store: each image re-encoded to JPEG, photos at most 800 px on the long side at quality 75, drawings 1,280 px at 80 so their text stays readable, never upscaled (EXIF orientation applied, transparency on white). Content-addressed: `data/media/<sha256[:2]>/<sha256>.jpg`, the name being the hash of the stored bytes.
- Deduplicated in the write path, from the first download: downloads run in threads (at most 4 per host, 0.25 s apart, 429/5xx/network errors retried with backoff; a host that refuses 20 in a row with 401/403 is skipped for the rest of the run), and one serial writer decides for each: the same bytes already stored -> `same_as` itself; else a stored file of the same place (the URL's place, or its listing before it has one) and kind within `PHOTO_MAX_DISTANCE` = 6 pHash bits (drawings: 0, only against drawings) -> `same_as` that file; else write. Whichever copy arrived first is the stored one; a larger later copy is not re-written (its original size is in its row, so the better source is derivable).
- Cap: before each write the running total of `stored_bytes` is checked against `max_gb`; at the cap the run stops and logs "media store full (5.0 GB)" (`runs.counts.full`, shown by the pipeline's Photos stage). So URLs go in priority order: active listings first, then places that pass or need a check on a goal, then drawings, then the first 12 photos of each listing, then the rest.
- Each run is a `runs` row (component `media`) with counts per outcome and host.
- Hosts in `[media] curl_hosts` (Furnished Finder's `staticproperties.furnishedfinder.com`) are downloaded with the `curl` binary (`--fail`, 30 s timeout, same UA and Referer, no proxy), because they answer 403 to Python's HTTP client and 200 to curl from the same machine; everything after the download (writer, dedupe, cap, log) is the same. SVG drawings (Prometheus) are rasterised with cairosvg (`unsafe=False`: no entities, no external fetches) at 1,280 px and stored as JPEG like any drawing. Drawings dedupe on identical stored bytes only.
- Hosts that refuse this machine (`[media] residential_hosts`, empty today; it did not help Furnished Finder) go through Apify's US residential proxy (`groups-RESIDENTIAL,country-US`; the proxy password is read from the Apify API with `APIFY_TOKEN` at run time, never printed or stored). It bills by traffic (about $8 per GB), so bytes through it are counted (`runs.counts.proxy_bytes`) and capped per run (`residential_max_mb`, default 300), and a smaller variant the host serves is tried first (Furnished Finder: `-650-570` instead of the `-full` original). The `media` row keeps the URL the source gave. `--host H` limits a run to one host; with `--retry-failed` it retries that host's earlier 403s (new rows).

Unknown terms are never 0: the card says '+ ? (n unknown)'. All shows no net commute. A `net_commute` rule (agg, ≤ max) makes it a requirement; any unknown term makes it needs_check, an estimate near the limit too.
- Status ticks and the view controls also govern which pins are drawn; all three statuses are shown by default, with fails dimmed.
- Cards show which attribute a place fails on: each goal result in `/api/places` carries `fails`, one `{s, f, v, lim?, pt?/set?, modes?}` per non-pass rule in `reasons` order (`filter.rules.fact`: the field or beds / baths / available / commute / near / amenity it judges and the deciding listing's value). The card colours that fact red (fail) or amber (needs_check): price spans (temp's price on the stay price, other goals' on the lease price; the deciding listing's own price follows in brackets when it differs from the card's minimum), beds, baths, the selected commute and each commute row of the selected goal (shown on the card with its time) with the same point and a mode the rule allows. An attribute the card does not show gets a small outlined chip ("term long", "private bath ?"). Only the selected goal; All shows every goal's. A commute row with no time is amber when its rule is undecided.
- Old saved list filters (annotation view / list / filters, a browser's `aptf.listFilters`) are no longer offered: goals come from `goals.toml` and the editor. The stored annotations stay (append-only) and old localStorage is ignored.

### eval (`aptf-eval`)
- Goal: the discovery benchmark for goal 2.
- Inputs: `eval/benchmark.csv` (copy of the user's sheet, snapshot of Nov 23, 2026), `places`.
- Outputs: `aptf-eval recall` prints found and missed per tier (Zillow listings, community sites, ruled out). A miss is reported with a reason: taken down since the snapshot (not counted) or not found (counted); the user decides when unclear. The sheet's "Walk to Caltrain" and "Drive to Meta HQ" columns also check the commute module (within about 2 minutes).

No LLM step is planned. If free-text parsing needs a model (direct property sites are the likely case), it is proposed to the user then, with accuracy measured through `checks`.
